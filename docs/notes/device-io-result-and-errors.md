# Structured Device I/O Results and Python Exceptions

Date: 2026-08-16

Status: planning. No implementation has been started.

## Goal

Replace the boolean result of the public C++ `Device::read()` and
`Device::write()` APIs with an operation-scoped result that identifies why the
operation failed and carries the exact parsing or playing messages generated by
the transient event engine.

Upgrade `ChannelManager` and the CORBA channel transport in the same change so
the result remains intact for local devices, partner devices, remote devices,
and Python callers. Python `Device.read()` and `Device.write()` should raise a
`DeviceIOError` on failure rather than returning `None` or `False` without an
explanation.

The result must belong to the specific read/write call. Do not implement this
by querying engine 0 for its most recent result after the call returns. A
separate "last result" lookup is subject to stale results and races and cannot
represent validation, transport, or payload-conversion failures.

## Naming

Use two related names with distinct purposes:

- `DeviceIOResult` is the C++ value returned by `Device` and `ChannelManager`.
  It represents both success and failure. A successful result may still carry
  warnings or informational engine messages.
- `DeviceIOError` is the Python exception raised for an unsuccessful
  `DeviceIOResult`. The exception should retain the complete result as a
  `result` attribute.

Do not name the C++ return value `DeviceIOError`: an error-only name is
misleading for a value returned on every successful operation.

## Current Behavior

The public C++ interface currently returns only `bool`:

```cpp
virtual bool write(short channel, const STI::Utils::MixedValue& value) = 0;
virtual bool read(short channel, STI::Utils::MixedValue& data) = 0;
virtual bool read(short channel, const STI::Utils::MixedValue& value,
                  STI::Utils::MixedValue& data) = 0;
```

`LocalDevice::read()` validates the channel, direction, argument type, channel
implementation result, and returned data type. `LocalDevice::write()` performs
the corresponding output checks. All of those failures collapse to `false`.

The default `LocalDevice` read/write pathway creates a
`SingleUndocumented` shot in transient engine pool 0. `playSingleEvent()` owns
the exact `ParseTicket` and `ResultTicket`, but the public read/write return path
discards their IDs and messages.

The Python bindings currently behave differently for reads and writes:

- `DevicePy::write()` returns the C++ boolean.
- `DevicePy::read()` returns the converted value on success and `None` on
  failure.
- A successful `MixedValueType::Empty` read also converts to `None`, so Python
  cannot distinguish that success from failure.

The latest transient-engine messages can be inspected manually through
`getLastParseResult(EngineID(0))` and `getLastShotResult(EngineID(0))`, but this
is not a correct per-operation error channel:

- parse failure may not create a new shot result;
- validation and direct channel-hook failures may create no engine result;
- CORBA and client-side payload conversion failures occur outside the device
  engine;
- another caller can replace the engine's latest result before the lookup;
- a stale shot can be mistaken for the failed operation.

## Locked Design Decisions

1. **Return a structured result from C++.** `Device::read()`,
   `Device::write()`, `ChannelManager::readChannel()`, and
   `ChannelManager::writeChannel()` return `DeviceIOResult`.

2. **Keep the read data output parameter.** The result reports status and
   diagnostics; `MixedValue& data` remains the read payload destination. This
   limits unrelated call-site churn and avoids forcing another potentially
   large `MixedValue` copy.

3. **Leave read output unchanged on failure.** Implementations should collect
   data into a local temporary and assign the caller's `data` only after the
   operation and result-type validation succeed.

4. **No implicit boolean conversion.** Do not add `operator bool()` to
   `DeviceIOResult`. Callers must explicitly use `.success`, which makes the API
   migration visible and prevents new code from silently discarding errors.

5. **Preserve legacy device-driver hooks.** Existing derived devices may keep
   overriding boolean `readChannel()` and `writeChannel()`. `LocalDevice`
   converts `false` into a generic structured channel-operation error when the
   hook did not report a more specific failure. This avoids requiring every
   `LocalDevice` driver to change in the same release.

6. **Use exact tickets, not engine-last lookup.** The default pipeline copies
   parse IDs, shot IDs, and messages directly from its `ParseTicket` and
   `ResultTicket` into the active `DeviceIOResult`.

7. **Upgrade ChannelManager and CORBA together.** A `RemoteDevice` cannot
   construct the server's detailed result if `RemoteChannelManager` receives
   only a boolean.

8. **Keep the wire upgrade additive initially.** Add structured CORBA
   operations while retaining the existing boolean operations. This permits
   old clients to call new servers and lets new clients fall back when talking
   to an old server.

9. **Python throws on failure.** Python `Device.read()` returns the converted
   read value on success. Python `Device.write()` returns `True` on success.
   Both raise `DeviceIOError` on failure.

10. **C++ does not throw for ordinary device failure.** C++ callers inspect the
    returned result. Exceptions remain reserved for programming errors or
    exceptional runtime failures not expressible by the result contract.

## Public C++ Types

Add a public header, recommended path:

```text
include/sti/device/DeviceIOResult.h
```

Use the project header-guard convention:

```cpp
#ifndef STI_DEVICE_DEVICEIORESULT_H
#define STI_DEVICE_DEVICEIORESULT_H
```

Recommended public shape:

```cpp
namespace STI::Device
{

enum class DeviceIOOperation
{
    Read,
    Write
};

enum class DeviceIOFailureStage
{
    None,
    DeviceUnavailable,
    ChannelLookup,
    ChannelDirection,
    ArgumentValidation,
    ChannelOperation,
    Parse,
    Play,
    MeasurementCollection,
    ResultValidation,
    Transport,
    PayloadConversion
};

struct [[nodiscard]] DeviceIOResult
{
    bool success{false};
    DeviceIOOperation operation{DeviceIOOperation::Read};
    short channel{-1};
    DeviceID deviceID;
    DeviceIOFailureStage failureStage{DeviceIOFailureStage::None};

    std::optional<STI::Engine::ParseID> parseID;
    std::optional<STI::Engine::ShotID> shotID;

    // Layer-local fallback or summary. Engine messages remain structured below.
    std::string message;
    std::vector<STI::Engine::EngineParsingMessage> parsingMessages;
    std::vector<STI::Engine::EnginePlayingMessage> playingMessages;

    bool hasErrors() const;
    std::string formatMessage() const;
};

} // namespace STI::Device
```

Small named factories are recommended so every return path initializes context
consistently, for example:

```cpp
DeviceIOResult makeDeviceIOSuccess(DeviceIOOperation operation,
                                   short channel,
                                   const DeviceID& deviceID);

DeviceIOResult makeDeviceIOFailure(DeviceIOOperation operation,
                                   short channel,
                                   const DeviceID& deviceID,
                                   DeviceIOFailureStage stage,
                                   const std::string& message);
```

Prefer class methods or functions in `DeviceIOResult.cpp` over anonymous
file-local formatting helpers. Add the implementation file to
`src/device/src/CMakeLists.txt`.

Marking the result type `[[nodiscard]]` is recommended. Some existing calls
ignore the boolean return entirely, so changing the return type alone would not
make those sites visible during migration. The attribute makes discarded
diagnostics a compiler warning without adding an implicit boolean conversion.

### Success and message semantics

- `success == true` means the requested operation completed and, for a read,
  `data` contains a type-valid result.
- A successful result may contain warning or informational parsing/playing
  messages.
- Any parsing or playing message with type `Error` makes the operation fail.
- `failureStage == None` on success.
- On failure, `failureStage` identifies the layer that rejected or failed the
  operation. `message` provides a fallback when no engine message exists.
- Do not copy formatted strings into the structured message vectors. Preserve
  the original `sourceID`, ID code, name, and message.

### Formatting

`formatMessage()` should be deterministic and suitable for exception text. It
should include:

1. operation, device ID, and channel;
2. failure stage;
3. each parsing error, in stored order;
4. each playing error, in stored order;
5. the fallback `message` when it adds information or when no engine error is
   present.

Warnings and informational messages should remain available through the result
but should not dominate the exception string. Avoid embedding log paths as the
only explanation.

## LocalDevice Pipeline

### Validation failures

`LocalDevice::write()` should distinguish at least:

- missing channel: `ChannelLookup`;
- channel is not an output: `ChannelDirection`;
- value does not match `Channel::getOutputType()`: `ArgumentValidation`;
- `writeChannel()` returned false without a reported detail:
  `ChannelOperation`;
- successful hook: save `lastValue` and return success.

`LocalDevice::read()` should distinguish at least:

- missing channel: `ChannelLookup`;
- channel is not an input: `ChannelDirection`;
- read argument does not match `Channel::getOutputType()`:
  `ArgumentValidation`;
- `readChannel()` returned false without a reported detail:
  `ChannelOperation`;
- returned data does not match `Channel::getInputType()`:
  `ResultValidation`;
- successful hook and result validation: commit tracked read files, update
  channel state, assign the caller's output, and return success.

Failed reads must discard helper-owned virtual files created during that call,
as they do today. A failed read must not update `lastValue` or
`lastMeasurement`.

### Bridging existing boolean channel hooks

Keep these virtual driver hooks boolean:

```cpp
virtual bool writeChannel(short channel, const MixedValue& value);
virtual bool readChannel(short channel, const MixedValue& value,
                         MixedValue& data);
```

Use an operation-scoped result builder to bridge detailed failures across this
legacy virtual boundary. The recommended implementation is an RAII scope in
`LocalDeviceHelpers.h/.cpp`, replacing or subsuming the current
`ReadFailureReportScope`:

```cpp
class DeviceIOResultScope
{
public:
    explicit DeviceIOResultScope(DeviceIOResult& result);
    ~DeviceIOResultScope();

    static DeviceIOResult* current();
    static void merge(const DeviceIOResult& result);
    static void report(DeviceIOFailureStage stage,
                       const std::string& message);
};
```

The active pointer may be `thread_local`, with nesting restored in the
destructor. It exists only during a call and must never become a public
"last error" store. Internal code should pass a result explicitly where
practical; the scope is specifically for crossing existing virtual hook
signatures without breaking every device driver.

If a driver hook returns false and the scope has no error yet, `LocalDevice`
adds the generic `ChannelOperation` error. A future driver may report a more
specific error through a narrow protected helper, but existing drivers require
no source change.

### Default single-event pipeline

Refactor `playSingleEvent()` to return `DeviceIOResult` while retaining its
`ResultTicket` output when needed by reads:

```cpp
DeviceIOResult playSingleEvent(
    const STI::Engine::RawEvent& event,
    std::shared_ptr<STI::Engine::ResultTicket>& resultTicket);
```

The result should be populated from the exact tickets owned by this call:

1. Create and submit the transient parse job in engine pool 0.
2. Create the `ParseTicket`, wait, and always copy its parse ID and parsing
   messages when available.
3. If the parse ticket does not complete or contains parsing errors, return
   `success=false`, `failureStage=Parse`. Do not query the scheduler's latest
   parse result.
4. Submit play only after successful parse.
5. Create the `ResultTicket`, wait, and always copy its shot ID and playing
   messages when available.
6. If the result ticket does not complete or contains playing errors, return
   `success=false`, `failureStage=Play`.
7. Otherwise return success, preserving warnings and informational messages.

`readChannelDefault()` then examines the exact ticket measurements. Missing,
null, not-ready, or otherwise unavailable measurement data should return
`MeasurementCollection`. Incorrect final `MixedValue` type remains
`ResultValidation` in the public read layer.

The boolean `readChannelDefault()` and `writeChannelDefault()` entry points used
by existing Python/Java device delegates may remain as compatibility wrappers.
They should call structured private/default helpers, merge the returned result
into the active `DeviceIOResultScope`, and return `.success`.

### PseudoSynchronousEvent

`PseudoSynchronousEvent` currently converts a false result into generic
`"Device read failed"` or `"Device write failed"` playing messages. Update it
to inspect `DeviceIOResult`:

- use `.success` for control flow;
- copy meaningful nested parsing/playing errors into the synchronous event when
  they are not already represented by the outer shot;
- add one generic playing error only when the result has no structured engine
  error;
- include the result's failure stage and fallback text in that generic error;
- avoid duplicating the same engine message in the final `ShotResult`.

This preserves engine message visibility for pseudo events while allowing a
direct caller to receive the same underlying failure.

## ChannelManager Behavior

`LocalChannelManager` should return the exact `DeviceIOResult` from its owning
`LocalDevice`. A missing channel-manager entry should produce a
`ChannelLookup` result rather than `false`; a null owning `LocalDevice` should
produce `DeviceUnavailable`.

`LocalChannelManager::loadProfile()` remains a boolean profile operation. Its
multi-channel loop must inspect each write result's `.success`, retain its
existing aggregate-success behavior, and log or otherwise surface each
formatted failure. It does not return one arbitrarily selected
`DeviceIOResult` for the whole profile load.

`PartnerDevice` should return the partner manager's result unchanged. If the
partner or manager is unavailable, it should construct a
`DeviceUnavailable` result with the partner ID and requested channel.

`RemoteDevice` should return the remote manager's result unchanged. If it
cannot obtain a manager, it should return `DeviceUnavailable`.

`NetworkDevice` should forward its wrapped `LocalDevice` result. If its wrapped
device is missing, it should return `DeviceUnavailable`.

`Logger` read/write tasks should use `.success`. For failures, log the formatted
result instead of only `"Failed"`; take care not to produce unbounded multiline
log records if several engine messages are present.

## CORBA Transport

### IDL record

Add transport equivalents to `src/network/idl/orbTypes.idl`. CORBA IDL has no
`std::optional`, so use explicit presence flags:

```idl
enum TDeviceIOOperation {
    TDeviceIORead,
    TDeviceIOWrite
};

enum TDeviceIOFailureStage {
    TDeviceIONone,
    TDeviceIODeviceUnavailable,
    TDeviceIOChannelLookup,
    TDeviceIOChannelDirection,
    TDeviceIOArgumentValidation,
    TDeviceIOChannelOperation,
    TDeviceIOParse,
    TDeviceIOPlay,
    TDeviceIOMeasurementCollection,
    TDeviceIOResultValidation,
    TDeviceIOTransport,
    TDeviceIOPayloadConversion
};

struct TDeviceIOResult {
    boolean success;
    TDeviceIOOperation operation;
    short channel;
    TDeviceID deviceID;
    TDeviceIOFailureStage failureStage;

    boolean hasParseID;
    TParseID parseID;
    boolean hasShotID;
    TShotID shotID;

    string message;
    TEngineParsingMessageSeq parsingMessages;
    TEnginePlayingMessageSeq playingMessages;
};
```

The existing parsing and playing message records already carry source IDs,
message ID codes, names, and text and should be reused.

### Additive TChannelManager operations

Retain the existing boolean operations during the transition and add distinct
structured operations in `src/network/idl/deviceNet.idl`:

```idl
interface TChannelManager
{
    // Existing compatibility operations.
    boolean writeChannel(in short channel, in TMixedValue value);
    boolean readChannel(in short channel, in TMixedValue value,
                        out TMixedValue data);

    // New operations.
    TDeviceIOResult writeChannelResult(in short channel,
                                       in TMixedValue value);
    TDeviceIOResult readChannelResult(in short channel,
                                      in TMixedValue value,
                                      out TMixedValue data);
};
```

The servant's old methods should call the new C++ `ChannelManager` operations
and return only `.success`. This keeps old clients functional against a new
server. Both old and new read operations must initialize the CORBA `out`
payload even on failure; use an empty `TMixedValue` when no read value is
available.

`RemoteChannelManager` should prefer the new operations. If a server responds
with `CORBA::BAD_OPERATION`, it should retry the old boolean method and return a
generic result. That fallback result should state that detailed diagnostics are
unavailable from the legacy remote endpoint. Other CORBA exceptions produce
`failureStage=Transport` and include the exception name in `message`.

Conversion of an incoming `TMixedValue` in `TChannelManager_i` happens before
the device operation. Catch conversion failures in the servant and return a
`PayloadConversion` result instead of allowing them to become an unexplained
CORBA exception. The same rule applies to the read argument and write value.

If the server reports success but conversion of the returned `TMixedValue`
fails on the client, preserve the server result's IDs and messages but change:

- `success=false`;
- `failureStage=PayloadConversion`;
- `message` to a client-side conversion explanation.

Never query remote engine 0 after a channel RPC to fill the result.

## Python API

### Bound result

`stidevicepy`. The result binding should expose read-only fields plus
`hasErrors()` and `formatMessage()`.

Recommended files:

```text

src/stipy/stidevicepy/src/DevicePy.cpp
src/stipy/stidevicepy/src/Device_wrap.cpp
src/stipy/stidevicepy/src/ChannelManagerPy.cpp
src/stipy/stidevicepy/src/ChannelManager_wrap.cpp
src/stipy/stidevicepy/src/pywrapper.cpp
src/stipy/stidevicepy/src/CMakeLists.txt
```

### Exception contract

Register `DeviceIOError` as a Python `RuntimeError` subclass. The native C++
exception/translator should retain the originating `DeviceIOResult` and attach
it to the Python exception as `.result`.

Initialize the result enums, result class, and exception type in
`pywrapper.cpp` before `init_ChannelManager()` and `init_Device()`. Put the
exception construction in one binding helper so `DevicePy` and
`ChannelManagerPy` cannot diverge. The helper should instantiate
`DeviceIOError(result.formatMessage())`, attach `py::cast(result)` as
`.result`, set the Python error, and throw `pybind11::error_already_set`.

Expected use:

```python
try:
    image = device.read(0)
except stidevicepy.DeviceIOError as exc:
    print(exc)
    print(exc.result.failureStage)
    for message in exc.result.playingMessages:
        print(message.getName(), message.getMessage())
```

Regular Python methods behave as follows:

- `Device.read(channel[, value])`: on success, return the converted data; on
  failure, raise `DeviceIOError`.
- `Device.write(channel, value)`: on success, return `True`; on failure, raise
  `DeviceIOError`.
- A successful empty read returns `None` without raising. Failure is therefore
  no longer ambiguous with `MixedValueType::Empty`.

Also expose non-throwing diagnostic entry points so callers that prefer results
do not have to catch exceptions:

```python
result, data = device.readResult(channel, value=None)
result = device.writeResult(channel, value)
```

Use Python naming consistent with the rest of `stidevicepy` if snake_case is
preferred during implementation, but document one canonical form.

`ChannelManagerPy` should follow the same rule: normal channel operations throw
on failure, and explicit result-returning methods remain available.

### Python-authored devices

Existing Python `writeChannel()` and `readChannel()` driver overrides do not
need to return `DeviceIOResult` in the first implementation. Preserve their
current success contracts and bridge failures through `LocalDevice`.

As a related correction, `LocalDeviceDelegate::readChannel()` currently always
returns true after converting the Python return value. Update the behavior so:

- a Python exception becomes a structured `ChannelOperation` failure and is
  rethrown or translated safely at the public Python boundary;
- `None` is successful only when it is a type-valid empty read result;
- non-empty input channels returning `None` fail normal result validation;
- Python `writeChannel()` returning false becomes a structured generic failure.

Do not let a Python exception escape an event-engine worker thread without being
converted into the operation/playing-message system.

## Java/SWIG

The Java wrapper is not part of the default top-level build, but `JDevice`
directly implements `Device` and will no longer compile until updated.

At minimum:

- update `JDevice` to implement the structured C++ virtual methods;
- keep Java-facing `JLocalDevice.write(int, ...)` and `read(int, ...)`
  conveniences stable where possible by translating `.success` and throwing a
  Java exception on failure;
- update `JChannelManager` if ChannelManager is exposed;
- add SWIG declarations or typemaps for the result/error contract;
- regenerate `sti_wrap.cpp`, `sti_wrap.h`, and generated Java sources rather
  than editing them manually.

If Java is no longer supported, explicitly document that decision instead of
leaving an uncompilable optional target.

## ABI and Versioning

Changing a public virtual return type is an ABI break. Every binary linked to
`stidevice` must be rebuilt even when its source only derives from
`LocalDevice` and requires no edits. This includes:

- `stinetwork`;
- `stidevicepy` and `stipy`;
- server libraries;
- external C++ device libraries such as `sti3-devices`;
- the optional Java native wrapper;
- external C++ frontends.

Do not mix old and new `stidevice` consumers in one installation. Packaging
must force a coordinated clean rebuild. Because this is a breaking change, the
release/ABI version policy should be reviewed before placing it in a patch-level
release.

The additive CORBA method plan reduces rolling-upgrade risk, but it does not
remove the local C++ ABI break.

## Implementation Phases

These phases may be separate commits, but they must ship as one coherent API
upgrade so no public layer permanently drops diagnostics.

### Phase A: Core types and public API

1. Add `DeviceIOResult` types, formatting, factories, and unit tests.
2. Change `Device` and `ChannelManager` virtual return types.
3. Update direct implementations and test doubles enough to compile.
4. Do not add implicit boolean conversion.

### Phase B: Local operation pipeline

1. Add the operation-scoped result bridge in `LocalDeviceHelpers`.
2. Populate validation and channel-hook failures.
3. Return exact parse/result ticket IDs and messages from the default pipeline.
4. Preserve read-file cleanup and channel-cache semantics.
5. Update `PseudoSynchronousEvent` message forwarding/deduplication.

### Phase C: ChannelManager and CORBA

1. Make local and partner managers preserve the structured result.
2. Add IDL types and additive result operations.
3. Add converters and regenerate omniORB stubs.
4. Update servant and remote manager, including legacy fallback.
5. Add transport, conversion, and local/remote parity tests.

### Phase D: Python

1. Bind the result types.
2. Add `DeviceIOError` with `.result`.
3. Make normal Device and ChannelManager operations throw on failure.
4. Add non-throwing result methods.
5. Correct Python-authored read-channel failure handling.

### Phase E: Remaining consumers

1. Update Logger and active tests.
2. Update C++ and Python examples and user documentation.
3. Update or explicitly retire the Java/SWIG path.
4. Rebuild all downstream device libraries and frontends.

## Test Plan

### Core result tests

- Factory/default construction initializes every field consistently.
- `hasErrors()` detects parsing and playing errors but not warnings/info.
- `formatMessage()` is deterministic and includes device/channel/stage context.
- Success can carry warnings without becoming failure.
- Every failure-stage enum round-trips through its string/conversion helpers.

### LocalDevice tests

- Missing channel returns `ChannelLookup` for both read and write.
- Wrong channel direction returns `ChannelDirection`.
- Wrong argument type returns `ArgumentValidation` with expected/actual types.
- Boolean driver hook false returns `ChannelOperation` when no detail was
  reported.
- Invalid read result type returns `ResultValidation`, leaves caller output and
  channel caches unchanged, and discards helper-created files.
- Successful read assigns output and updates `lastMeasurement`.
- Successful write updates `lastValue`.
- Parse failure returns the exact parse ID and parsing messages.
- Play failure returns the exact shot ID and playing messages.
- A successful operation preserves engine warnings.
- Missing/null/not-ready measurement returns `MeasurementCollection`.
- Slow camera-style reads still wait according to the current no-fixed-one-
  second-timeout behavior.
- Image/File/Binary results continue to transfer successfully.
- Two concurrent callers never receive each other's IDs or messages.

### Pseudo-event tests

- A nested read/write failure appears in the outer shot result.
- Existing structured messages are not duplicated by a generic wrapper error.
- A generic playing error is added when a legacy hook supplies only false.

### ChannelManager tests

- Local manager returns the same result fields as direct LocalDevice access.
- PartnerDevice preserves the target result.
- Missing manager/device produces `DeviceUnavailable`.
- Logger records a useful concise failure summary.

### Network tests

- `DeviceIOOperation` and every `DeviceIOFailureStage` round-trip through IDL.
- `TDeviceIOResult` round-trips both optional-ID states and both message lists.
- Old boolean servant operations return `.success` from the structured C++
  result.
- New remote operations preserve stage, IDs, messages, and fallback text.
- New client fallback against a legacy endpoint returns a generic result without
  stale engine lookup.
- CORBA exceptions become `Transport` failures.
- Client-side `MixedValue` conversion failure becomes `PayloadConversion` while
  preserving server diagnostics.
- Remote Image/File/Binary success behavior remains covered.

### Python tests

- Failed read raises `DeviceIOError`, not `None`.
- Failed write raises `DeviceIOError`, not `False`.
- The exception string uses `formatMessage()` and `.result` exposes all fields.
- Successful empty read returns `None` without raising.
- Successful write returns `True`.
- Successful scalar, vector, Binary, File, and Image reads retain current Python
  values.
- Non-throwing result methods expose failures without raising.
- Python-authored device callback failure becomes a structured error and does
  not escape an engine worker thread unhandled.

## Acceptance Criteria

The change is complete when:

- every public C++ Device and ChannelManager read/write call returns
  `DeviceIOResult`;
- a failed local or remote operation reports the failure stage and an actionable
  message without consulting the transient engine's latest result;
- exact parse/shot IDs and engine messages are preserved when an engine job was
  created;
- Python normal calls raise `DeviceIOError` with the same structured result;
- old CORBA boolean clients remain functional against a new server;
- new clients degrade to a generic result against an old server;
- all C++/network/Python tests pass;
- C++ and Python examples document the new failure handling;
- downstream device binaries are rebuilt against the new ABI.

## Open Questions

- Should the first release expose a protected `LocalDevice::reportIOFailure()`
  helper so legacy boolean driver hooks can provide detailed hardware errors
  without changing their signatures?
- Should warnings and informational messages be included in the default Python
  exception string, or only remain available through `exc.result`?
- What ABI/version number will identify the coordinated rebuild?
- Is the Java binding still supported, and if so should Java receive a bound
  result object, exceptions, or both?
