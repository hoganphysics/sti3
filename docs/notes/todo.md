
== Add EnginePlayingMessage messages to sti3 and stipy
- I have introduced a new message type called EnginePlayingMessage in the sti3 C++ device library. This message is used for messages generated while the EventEngine is running a play job.
  - This message is similar to the existing EngineParsingMessage used for parsing jobs.
  - The EnginePlayingMessage class is defined in `/include/sti/engine/EnginePlayingMessage.h`.
  - The message will be used to report when there are errors during play jobs in the LocalEventEngine, LocalEventEngineScheduler, and EventEngineManager classes.
  - Play messages (errors, warnings, info) can also be generated by user generated code via the SychronizedEvent class during play jobs.
- The EnginePlayingMessage list has been added to the following classes in the src/device library:
  - EngineSchedulerMessage (and also the message count in EngineJobUpdateDeviceMessage)
  - EventEngineJob (abstract base class for jobs)
  - LocalEventEngineJob (derived class for local jobs)
  - ResultTicket
  - ShotResult
  - SynchronousEvent (for adding play messages from user code)
- These changes must be propagated through the sti network library (src/network) and the stipy pybind11 wrapper (src/stipy) to ensure that play messages are correctly transmitted over the network and accessible from Python.
- The stipy pybind11 wrapper needs to be updated to expose the EnginePlayingMessage class and the play message lists in the relevant classes to Python, analogous to how parsing messages are currently exposed. The following wrappers need to be modified:
  - EnginePlayingMessage wrapper (does not exist yet)
  - SynchronousEvent wrapper (add play message accessors)
  - EventEngineJob wrapper (defined in LocalEventEngineJob wrapper, add play message accessors)
  - ResultTicket wrapper (wrapps PyResultTicket class, add play message accessors)
  - ShotResult wrapper (add play message accessors)
- The sti network library needs to be updated. I have already updated the corba IDL files to include the EnginePlayingMessage and EnginePlayingMessageCount definitions and have regenerated the corba stubs. The only changes are to structs, so there is no need to modify and servant implementations. However, the conversion functions need to be updated to handle the new play message lists.
  - Network conversion functions live in `src/network/src/convert/`.
  - The EngineParserMessage conversion functions are located in `Convert_EventEngine.h` and `Convert_EventEngine.cpp`. The new EnginePlayingMessage and EnginePlayingMessageCount conversion functions should be added here.
  - For the modifed structs that now include play message lists, conversion should use the same approach as parsing messages, using the new conversion functions for EnginePlayingMessage and EnginePlayingMessageCount.
  - The modified structs that need play message conversion added are:
    - EventEngineJob
    - ResultTicket
    - ShotResult
    - EngineSchedulerMessage (and also EngineJobUpdateDeviceMessage)
- We also need to update the LegacyExperimentXMLBuilder::build function in `src/server/src` to include play messages when building the XML representation of experiment results. This will ensure that any play messages generated during job execution are included in the XML output for experiment results.
  - The build function should add a new child element after the "parse" element called "messages". This new element will contain all the play messages from the ShotResult, including message type, source DeviceID, id code, message name, and message text.

== Use EnginePlayingMessage to indicate play errors in LocalEventEngine and LocalEventEngineScheduler
- I want to trace the full play shot path in the LocalEventEngine and LocalEventEngineScheduler classes to identify where play errors are occurring.
- Right now there, there are some return paths that do not generate any error messages when a play job fails. I want to ensure that all failure paths generate appropriate EnginePlayingMessage messages to indicate the nature of the error.
- In LocalEventEngine, I have began by updating LocalEventEngine::play(EventEngineJob& job) to generate errors generated during the work toward the PlayReady state. These errors are added to a list playReadyMessages and sent as a EngineSchedulerMessage named playReadyMessage.
  - Not all return paths have been checked yet; this is a work in progress.
  - In particular, owned devices process their own play job and then send a EngineSchedulerMessage back to the parent engine. These owned device messages are handled int LocalEventEngine::handlePlayReadyMessage.  handlePlayReadyMessage should append the playReadyMessages from the owned device to the parent job's play messages. Also, right now there are several "fail quiet" paths in handlePlayReadyMessage that need to be updated.
- The next step is LocalEventEngine::play(const EngineJobID& jobID, const std::shared_ptr<TriggerCallback>& triggerCB, bool debug), which handles the actual play execution after the PlayReady state is reached. This function also has several return paths that do not generate error messages. I want to update these paths to generate appropriate EnginePlayingMessage messages too.
  - Messages generated during play should be added to the EngineSchedulerMessage named playCompleteMessage once the play thread completed (for success or failure paths).
  - Similary to play read, the play function waits for owned devices to complete their play jobs and handles their EngineSchedulerMessages in LocalEventEngine::handlePlayCompleteMessage. This function also needs to be updated to append owned device play messages to the parent job's play messages.
- I added a convenience function LocalEventEngine::addPlayMessage to simplify adding play error messages to a list of messages. This can be used during each stage of the play process to add messages as needed.
  - Right now the play message lists are class-level std::vector<EnginePlayingMessage>, so they must be cleared at the start of each play job. 
- For both message handlers (handlePlayReadyMessage and handlePlayCompleteMessage), I need to ensure that any play messages from owned devices are correctly propagated to the parent job's play messages. If the message sourceID is not in the list of ownedTargets, the message should be ignored and not have its error appended.  Otherwise the incoming play messages should be appended to the parent job's play messages.
  - The only exceptions are if the message is null or if the message->jobID does not match the expected jobID. In that case, a warning message should be added instead (PlayingMessageType::Warning).
