## LocalEventEngineScheduler and EventEngineManager race condition bug

I think there is a race condition bug in the interaction between LocalEventEngineScheduler, LocalEventEngine and EventEngineManager during parsing job. This can cause the LocalEventEngineScheduler to get stuck waiting for a job that has already been completed in the LocalEventEngine, leading to a deadlock situation. The LocalEventEngineScheduler event loop will continue to hold the job in its runningJobs queue, even though the job has already finished processing in the LocalEventEngine.

I've noticed this when a device is parsing an event and has one dependent device that also has events to parse. When the bug happens, both devices's have LocalEventEngine is in the EngineState::Parsed state.  The dependent device LocalEventEngineScheduler has it's job complete, but the parent device LocalEventEngineScheduler is stuck waiting for the job to complete, even though the job has already been completed in the LocalEventEngine. I can verify this by checking the runningJobs queue in the LocalEventEngineScheduler, which still contains the job that has already been completed in the LocalEventEngine.

### Possible race condition scenario
- During a parsing job, the LocalEventEngine processes the job in the ``void LocalEventEngine::parse(STI::Engine::EventEngineJob& job)`` function.
- At the end of the parse function, LocalEventEngine generates a EngineSchedulerMessage called parseCompleteMessage. The message is first queued by the message handling system. It is placed in a message queue and then through the message handling system, this message is sent to the LocalEventEngineScheduler where it is handled by the ``void LocalEventEngineScheduler::handleMessage(const std::shared_ptr<EngineSchedulerMessage>& mess)`` function.
- The LocalEventEngineScheduler::handleMessage function passes the parseCompleteMessage to the job's EventEngineManager via the ``void EventEngineManager::handleParseMessage(const std::shared_ptr<STI::Device::EngineSchedulerMessage>& evt)`` function.
- The EventEngineManager then passes the message back to the LocalEventEngine via ``void LocalEventEngine::handleParseMessage(const std::shared_ptr<EngineSchedulerMessage>& message)``.
- If the message is too slow, then then the EventEngineManager may set running = false in runJob() before the message can be handled. This might cause EventEngineManager::handleParseMessage to drop the message because running is false.
- The message passing from LocalEventEngine::parse is important, because it is how the parent device's LocalEventEngineScheduler is notified that the job has completed in the dependent LocalEventEngine. If this message is dropped, then the parent device's LocalEventEngineScheduler will never be notified that the job has completed, and will continue to wait for the job to complete, leading to a deadlock situation.


I'm not sure if this is the exact scenario that is causing the race condition, because it seems like EventEngineManager alwasys should call either jobComplete or cancelJob after parse completes, regardless of the message arrival time. The bug is inconsistent, so it is hard to pin down the exact cause. But it seems likely that the message passing system and the timing of when running is set to false in EventEngineManager::runJob() is contributing to the race condition. When I test this with many rapid parse/play cylces, it works most of the time, but occasionally hits the deadlock situation where the job in LocalEventEngineScheduler never stops, even though the LocalEventEngine has reached the parse state.
